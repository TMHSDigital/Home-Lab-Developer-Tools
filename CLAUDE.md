# CLAUDE.md

Project documentation for Claude Code and AI assistants working on this repository.

## Project Overview

Home Lab Developer Tools integrates home lab and Raspberry Pi workflows into AI-assisted development. It includes 22 skills, 11 rules, and a companion MCP server with 56 tools for managing Docker Compose stacks, monitoring, DNS, reverse proxy, networking, backups, disaster recovery, security auditing, logs, notifications, OS management, certificates, multi-node, diagnostics, and system administration via SSH.

**Works with:** Cursor (plugin), Claude Code (terminal and in-editor), and any MCP-compatible client.

This is a monorepo -- the skills, rules, and companion MCP server live in the same repository. The MCP server connects to a Raspberry Pi via SSH to execute commands.

## Plugin Architecture

```
Home-Lab-Developer-Tools/
  .cursor-plugin/
    plugin.json              # Plugin manifest
  skills/
    <skill-name>/
      SKILL.md               # One skill per directory
  rules/
    <rule-name>.mdc           # Rule files
  mcp-server/
    src/
      index.ts               # MCP server entry point
      tool-registry.ts       # TOOLS map: every tool's register(); index.ts and tests use it
      tools/                 # One file per MCP tool
      utils/
        ssh-api.ts           # SSH connection helpers
        errors.ts            # Custom error classes
  docs/                      # Pages assets; index.html is generated by pages.yml (not tracked)
  tests/                     # Python structure tests
```

## Conventions

- Never use em dashes. Use regular dashes (-) or double dashes (--).
- Never use emojis.
- Tool names follow `homelab_camelCase`.
- Shared parameter names: `since` always uses `sinceSchema` from `utils/since-param.ts` (converted per backend); new tools size their output with `limit` (existing `lines` and `count` stay as they are); `service` is an exact container name.
- Each tool file exports a `register(server)` function that calls `server.registerTool(name, { description, inputSchema, annotations }, handler)` (never the deprecated `server.tool()`). Annotations come from `utils/annotations.ts`: `READ_ONLY`, `changesState(idempotent)`, or `destructive(idempotent)` for confirm-gated tools; `registration.test.ts` enforces them.
- All SSH interaction goes through `execSSH()` from `utils/ssh-api.ts`.
- Skills use kebab-case directory names with YAML frontmatter (`name`, `description`, `tools`).
- Rules use kebab-case filenames with `description` and `alwaysApply` frontmatter.

## Security

- Tools that change running state require `confirm=true`: `homelab_piReboot`, `homelab_backupRun`, `homelab_backupRestore`, `homelab_volumeBackup`, `homelab_certRenew`, `homelab_nodeExec`, `homelab_serviceRestart`, `homelab_composeUp`, `homelab_composeDown`, `homelab_adguardFilterToggle`, `homelab_alertSilence`, `homelab_systemdControl`, `homelab_grafanaImport`, and `homelab_aptUpdate` when `upgrade=true`. Use the shared `confirmParam` and `confirmCancelled` helpers from `utils/confirm-param.ts`; pass `confirmCancelled` a preview (`node` plus a lazy `commands` builder) so a call with `confirm: false` shows the target node and the masked command it would run, and runs nothing. `confirm` is a required boolean, so a call that omits it fails input validation (aptUpdate is the exception: there `confirm` is optional).
- `execSSH()` runs `assertCommandSafe()` before opening any SSH connection. This blocks catastrophic patterns (`rm -rf /`, `mkfs` on block devices, fork bombs, `poweroff`, etc.). Override with `HOMELAB_ALLOW_DANGEROUS_COMMANDS=true`.
- `HOMELAB_DRY_RUN=true` makes `execSSH` throw a `DryRunError` (from `utils/errors.ts`) describing the command instead of connecting; `errorResponse` turns it into a normal result, so tools never parse the plan as output. Multi-step tools stop at their first command. The command guard still runs in dry-run mode.
- No personal SSH usernames, hostnames, or key names in code or docs. Use `pi` / `raspberrypi.local` / `~/.ssh/id_ed25519` as generic defaults.

## Release Hygiene

Versions are never edited by hand: `release.yml` bumps the one shared version in `.cursor-plugin/plugin.json`, `mcp-server/package.json` and `mcp-server/package-lock.json` (the server reads its version from `package.json` at runtime), and the release doc sync updates the `Version` field above. A change that ships only needs:

| File | What to update |
|------|----------------|
| `CHANGELOG.md` | A line under `[Unreleased]`; `release.yml` moves it under the new version |
| `README.md`, `CLAUDE.md`, `mcp-server/README.md`, `mcp-tools.json` | Table rows for new tools, skills or rules |
| Tool, skill and rule counts | `.cursor-plugin/plugin.json` and `mcp-server/package.json` descriptions, README stat line, badge and category heading, `CLAUDE.md`, `mcp-server/README.md`, `AGENTS.md`, `site.json` |
| `ROADMAP.md` | Move finished items from Planned to the shipped version |
| GitHub repo About | Counts in the description (`gh repo edit --description "..."`), after the release |

`registration.test.ts` fails when a tool is missing from a table or a count is wrong in any of those files.

Checklist before pushing a change that ships:

1. All new tools listed in `mcp-server/src/tool-registry.ts` (index.ts registers everything in it)
2. All new tools have input validation tests
3. All new skills have SKILL.md with required frontmatter and sections
4. All new rules have .mdc with required frontmatter
5. Structure tests pass (`pytest tests/ -v`)
6. MCP server builds and tests pass (`npm run build && npm test`)
7. CHANGELOG.md `[Unreleased]` entry added
8. If dependencies changed, regenerate `package-lock.json` (`cd mcp-server && npm install`) and commit it

Publishing pipeline (fully automated):

1. Every push to `main` triggers `release.yml`. It releases only when shipped files (`mcp-server/` outside tests, `skills/`, `rules/`, `.cursor-plugin/`) changed since the last tag, and only after the build, Vitest and structure tests pass. The next version comes from commit messages (`feat:` = minor; `!` after any type, such as `feat!:`, or a `BREAKING CHANGE:` footer = major; anything else = patch)
2. `release.yml` bumps the version in `.cursor-plugin/plugin.json`, `mcp-server/package.json` and `mcp-server/package-lock.json` (one shared version; `index.ts` reads it from `package.json`), syncs release docs, pushes the commit and tag atomically, creates the GitHub Release, then dispatches `publish.yml`
3. `publish.yml` builds, tests, and publishes to npm via trusted publishing (OIDC, no `NPM_TOKEN`); the npm trusted publisher is bound to this filename, so publishing must stay in `publish.yml`
4. Never create tags, releases, or npm publishes manually

## Home Lab Context

The target environment is a Raspberry Pi 5 running:
- 13 Docker containers (Prometheus, Grafana, AdGuard, NPM, Portainer, Homepage, Uptime Kuma, Vaultwarden, Ntfy, Syncthing, Code Server, Stirling PDF, Speedtest Tracker)
- Native services: Cockpit (:9090), Samba (:445), node_exporter (:9100)
- Docker Compose stacks at `/opt/homelab/docker/` split into: base, monitoring, network, apps, security, storage, tools
- Restic backups via systemd timer
- Management from Windows via SSH and PowerShell
